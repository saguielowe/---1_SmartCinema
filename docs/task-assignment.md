# 分工草案

这份文档先给出默认分工边界，目的是减少并行开发时的互相改代码。后面可以换人，但尽量不要频繁改模块边界。

## 4 个模块

### A：座位渲染与选座交互

负责内容：

- Canvas 绘制影厅与银幕
- 座位数据渲染
- 手动选座、取消选座、多选交互
- 推荐座位高亮
- 向其他模块输出当前已选座位

输入：

- `hall`
- `seatState`
- `recommendationResult.recommendedSeatIds`

输出：

- `selectedSeatIds`

### B：智能推荐与评分逻辑

负责内容：

- 用户条件表单对应的推荐逻辑
- 连续座位搜索
- 情侣、家庭、团体规则
- 少年/老年限制规则
- 观影体验评分与推荐理由

输入：

- `recommendationInput`
- `hall`
- `seatState`

输出：

- `recommendationResult`

### C：订单中心与数据状态

负责内容：

- 登录注册
- 普通用户 / 管理员区分
- 订单中心
- LocalStorage 数据结构
- 座位售卖状态持久化
- 热度数据统计

输入：

- `selectedSeatIds`
- `user`
- `schedule`

输出：

- `seatState`
- `orders`
- `heatMapData`
- `authState`

### D：UI 整合与测试文档

负责内容：

- 页面结构整合
- 响应式布局
- 无障碍模式
- 表单与模块串联
- 联调测试
- 说明文档、用户手册、AI 使用记录整合

说明：

- D 不一定“包办杂活”，重点是保证最终体验成型
- 如果 UI 同学负责样式设计，建议与 D 紧密协作

## 推荐认领方式

- 先按兴趣认领主模块
- 如果暂时没人认领，默认先按这份边界推进
- 文档和字段变更优先改仓库，不在群里反复刷消息

## 联调顺序

1. C 先给出基础测试数据
2. A 先接 `hall + seatState`
3. B 在固定输入输出后独立开发推荐逻辑
4. D 最后把表单、推荐、选座、订单流程串起来

## 风险提醒

- A 和 B 不要各自定义一套座位 id
- B 和 C 不要各自定义一套用户输入字段
- D 不要在未同步的情况下直接改业务字段名
- 新增字段尽量“只增不乱改”
